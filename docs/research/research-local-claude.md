# Resilience & Recoverability Patterns in Agentic Workflow Orchestration (2024–2026)

**Decision context:** hardening Claude Code's Workflow tool runtime (parallel()/pipeline() JS fan-out, append-only `journal.jsonl` keyed by sha256 prompt-chain, cache-prefix replay on resume, zero retries — API errors are terminal and the run reports `completed`) via a macOS-installable patch layer.

## Executive Summary

- **(High Confidence)** Every mature durable-execution system retries by default with capped exponential backoff and classifies errors into retryable vs terminal via a thrown-type mechanism, not status-code tables: Temporal defaults to unlimited attempts at 1s×2.0 capped at 100s with `nonRetryableErrorTypes` [docs.temporal.io](https://docs.temporal.io/encyclopedia/retry-policies); Restate defaults to 500ms×2.0, cap 1m, **70 attempts, then `on-max-attempts = "pause"`** — parking the invocation for manual resume rather than killing it [docs.restate.dev](https://docs.restate.dev/references/server_config); Inngest defaults to 5 total attempts on a fixed backoff table (15s→2h) plus 0–30s additive jitter [github.com](https://github.com/inngest/inngest/blob/main/pkg/backoff/backoff.go). Claude Code's current zero-retry/terminal-null behavior is an outlier against every system surveyed.
- **(High Confidence)** The retryable/terminal split converges on three primitives worth copying verbatim: a `NonRetriableError`-style type that bypasses retries (Inngest, Restate `TerminalError`, Temporal `nonRetryable`) [inngest.com](https://www.inngest.com/docs/features/inngest-functions/error-retries/inngest-errors); a `RetryAfterError`/`next_retry_delay` that lets a 429's `Retry-After` header override computed backoff [docs.temporal.io](https://docs.temporal.io/ai-cookbook/http-retry-enhancement-python); and a predicate (`retry_on`, `shouldRetry`, `retry_condition_fn`) for everything else. Notably, LangGraph's default classifier retries 5xx and `ConnectionError` but **deliberately does not retry 429** [github.com](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py) — evidence the "always retry 429" assumption is contested.
- **(High Confidence)** For retry state persistence, all four durable-execution systems keep attempt counts and next-retry timestamps **outside the worker process** (Temporal server mutable state, Restate journal, Inngest platform store, DBOS Postgres rows) so worker death mid-backoff loses nothing [inngest.com](https://www.inngest.com/docs/learn/how-functions-are-executed). The journal.jsonl model maps directly onto DBOS's design (checkpoint completed steps only; in-flight retry counters are in-process and reset on recovery, guarded by a workflow-level `max_recovery_attempts=100` dead-letter cap) [docs.dbos.dev](https://docs.dbos.dev/explanations/system-tables).
- **(High Confidence)** Pause semantics have two distinct shapes the industry keeps separate: pause-a-single-task (Temporal Activity pause, Public Preview in server v1.28.0, with `--reset-attempts` interaction with retry counters) [docs.temporal.io](https://docs.temporal.io/activity-operations) and pause-the-workflow (Prefect's `pause_flow_run` keeps the process alive vs `suspend_flow_run` tears it down and re-runs from the top relying on task caching — exactly the cache-prefix-replay model) [docs-3.prefect.io](https://docs-3.prefect.io/v3/develop/pause-resume). Mature UIs encode a third family — degraded-but-live (`FAILING`, `soft_failed`, `neutral`/`skipped`) — so partial sibling failure renders as warning, not error [buildkite.com](https://buildkite.com/docs/apis/rest-api/builds).
- **(High Confidence)** For patching the minified `cli.js`, literal diffs (patch-package model) are the wrong primitive — they break every release. The proven prior art is Vencord's string-anchor + capture-group-regex patching with an `\i` any-identifier matcher, applied at load time (analogue: `Module.prototype._compile` source rewrite injected via `NODE_OPTIONS="--require"`), gated by fail-closed fingerprinting [deepwiki.com](https://deepwiki.com/Vendicated/Vencord/3.2.2-code-patching-mechanism). tweakcc's documented failures across Claude Code 2.1.49→2.1.76 (all regex-match misses) are the cautionary tale [github.com](https://github.com/Piebald-AI/tweakcc/issues/611). For retry injection *specifically*, a network-layer gateway via `ANTHROPIC_BASE_URL` (claude-code-router / LiteLLM pattern) is strictly more durable than any code patch — but cannot reach pause/resume, queue mutation, or UI concerns.
- **(Medium Confidence)** Live queue mutation is universally solved as a durable mailbox: Temporal Signals (fire-and-forget) vs Updates (validated, synchronous, GA; Update-with-Start GA'd in v1.28.0) [docs.temporal.io](https://docs.temporal.io/encyclopedia/workflow-message-passing), LangGraph's `Send` API for runtime-computed fan-out width [docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/graph-api), Airflow's `expand()` with a `max_map_length` default of 1024 [airflow.apache.org](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/dynamic-task-mapping.html).
- **(Medium Confidence)** Testing retry logic without real waits is a solved problem (Temporal time-skipping test env fast-forwards through retry backoff intervals [docs.temporal.io](https://docs.temporal.io/develop/typescript/testing-suite); `@sinonjs/fake-timers` `tickAsync` + undici `MockAgent` `.times(n)` fault sequences [github.com](https://github.com/nodejs/undici/blob/main/docs/docs/api/MockAgent.md)), but deterministic-simulation-grade chaos testing for *agent pipelines* is an open gap — 2025-era benchmarks (ReliabilityBench, ToolMaze, AgentNoiseBench) measure model behavior under faults, and no Toxiproxy-equivalent speaks the semantic LLM failure taxonomy (429-with-Retry-After, truncated SSE, malformed tool-call JSON) as first-class toxics.
- **(High Confidence)** claude-flow's "self-healing swarm" claims are predominantly marketing: issue #1397 (March 2026) documents that v3's agents "are database rows, not running processes," and the rebranded README has quietly dropped the self-healing/fault-tolerance/checkpoint claims [github.com](https://github.com/ruvnet/ruflo/issues/1397). Do not treat it as a design reference.

**Canonical backoff guidance.** AWS's Brooker analysis (2015, updated 2023): without jitter, N contending clients do O(N²) total work; **Full Jitter** — `sleep = random_between(0, min(cap, base·2^attempt))` — cut call counts by more than half at 100 clients and "should be considered a standard approach for remote clients" [aws.amazon.com](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/). Google SRE adds two budgets no orchestrator surveyed implements: max 3 attempts per request, and a per-client 10% retry-ratio budget ("A request will only be retried as long as this ratio is below 10%"), plus retry "only at the layer immediately above the layer that is rejecting them" [sre.google](https://sre.google/sre-book/handling-overload/).

**Design implications for the patch layer** — <INFERENCE from="Temporal/Restate/Inngest defaults; AWS Full Jitter; LangGraph's 429 exclusion; Anthropic SDK Retry-After behavior; SRE single-layer rule">a 30-retry cap with Full-Jitter exponential backoff (e.g. base 1s, ×2, cap 60–120s) is within surveyed norms only because Restate ships 70 and Temporal ships unlimited — but 30 attempts at cap ≈ 30–60 min of wall time, so the policy should be duration-bounded too (Restate's `maxRetryDuration`, Temporal's schedule-to-close). Classify: 429/529 → retry honoring `Retry-After` verbatim (Anthropic returns it; the SDK already sleeps it); 5xx/`overloaded_error` → retry with jitter; `ECONNREFUSED`/DNS failure → treat as *connectivity signal* feeding auto-pause (see 1.2), not a per-agent retry loop; 400/401/403/`invalid_request` → terminal. Critically, disable or account for the Anthropic SDK's own `max_retries=2` inside Claude Code to avoid multiplicative stacking — the retry-stacking hazard is documented across issue trackers (SDK sleeps full Retry-After, producing multi-minute hangs when layered)</INFERENCE>. The "usage limit reached" case is a distinct class: it has a known reset time, so the correct shape is Restate's `on-max-attempts = "pause"` — park the agent in a `paused` state with a scheduled auto-resume, not a backoff loop.

**Retry-state persistence for journal.jsonl.** The DBOS model is the direct analogue: completed step outcomes are durable; in-flight retry counters are process-local and reset on recovery, with a workflow-level dead-letter cap (`MAX_RECOVERY_ATTEMPTS_EXCEEDED` status) preventing infinite crash-loops [docs.dbos.dev](https://docs.dbos.dev/explanations/system-tables). <INFERENCE from="DBOS system-tables design; Temporal's decision to keep per-retry attempts out of event history">journal the retry *ledger* (attempt count, next-retry-at, last error class) as separate mutable-state records keyed by the same sha256 prompt-chain — not as journal result entries — so replay semantics stay clean and the history doesn't fill with retry noise, mirroring Temporal's explicit choice to keep attempts in mutable state "to avoid filling the Event History with noise"</INFERENCE>.

#### 1.2 Pause/resume semantics, connectivity-aware auto-pause, and UI states

**Task-level vs workflow-level pause.** Temporal now has both: workflow pause is landing natively (proto: `WORKFLOW_EXECUTION_STATUS_PAUSED`, `PauseWorkflowExecution`/`UnpauseWorkflowExecution` gRPC, `TemporalPauseInfo` search attribute; "the service won't dispatch new Workflow Tasks until it's unpaused") [github.com](https://github.com/temporalio/api/pull/653) [docs.temporal.io](https://docs.temporal.io/workflow-execution); Activity pause (Public Preview, server v1.28.0+) exposes the key retry interaction: `temporal activity unpause --reset-attempts` zeroes the attempt counter so a near-exhausted activity gets a fresh retry budget after unpause; a currently-executing attempt is not killed — pause gates *future* retries/schedules [docs.temporal.io](https://docs.temporal.io/activity-operations). Prefect's split is the other load-bearing distinction: `pause_flow_run` keeps the process alive (polling every 10s, default timeout 3600s, then the run fails); `suspend_flow_run` kills the process and on resume "the flow code will execute again from the beginning," relying on task caching to skip completed work [docs-3.prefect.io](https://docs-3.prefect.io/v3/develop/pause-resume). LangGraph's `interrupt()` requires a checkpointer + `thread_id`, restarts the whole node on resume (side effects before the interrupt must be idempotent), and delivers the resume payload as the `interrupt()` return value via `Command(resume=value)` [docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/interrupts). Inngest pauses at the *function* level (dashboard-only; events during pause are recorded as "skipped" runs and can be batch-replayed after resume) [inngest.com](https://www.inngest.com/docs/guides/pause-functions).

<INFERENCE from="Prefect suspend/caching; Workflow tool's existing cache-prefix replay; LangGraph node-restart semantics">The Workflow tool's journal-replay model is already Prefect-suspend-shaped: pause = stop dispatching new agent() calls + optionally abort in-flight ones; resume = re-run the script with cache-prefix replay. The patch layer therefore needs only (a) a dispatch gate checked before each agent() call, (b) a persisted `paused` flag + reason in run state, and (c) the existing resume path — no new checkpoint machinery. Per-agent pause (mid-LLM-call) is not worth building; the industry pauses at scheduling boundaries, not mid-request.</INFERENCE>

**Connectivity detection.** `navigator.onLine`/Electron `net.isOnline()` are documented as trustworthy only in the negative direction: "false if all network requests are guaranteed to fail… you should treat with care situations of getting false positives" [electronjs.org](https://www.electronjs.org/docs/latest/tutorial/online-offline-events). The production pattern is active probing: ChromeOS probes `generate_204` endpoints expecting an empty 204 (unambiguous, no redirects) [chromium.org](https://www.chromium.org/chromium-os/chromiumos-design-docs/network-portal-detection/); macOS probes `captive.apple.com`; `is-online` races parallel checks (HTTPS to icanhazip/Cloudflare, DNS to `myip.opendns.com`, Apple's captive-portal page) with a 5000ms default timeout, resolving true on first success [github.com](https://github.com/sindresorhus/is-online). Syncthing's reconnect cadence: probe disconnected peers every `reconnectionIntervalS=60` [docs.syncthing.net](https://docs.syncthing.net/users/config.html). On reconnect, resume with per-agent random delay drawn from the backoff window (Full Jitter) to avoid a synchronized reconnect storm [aws.amazon.com](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/). <INFERENCE from="ECONNREFUSED as terminal today; is-online design; Restate pause-on-exhaustion">the right macOS shape: on `ECONNREFUSED`/`ENOTFOUND`/`ETIMEDOUT`, run one probe (HEAD to `api.anthropic.com` or Apple's captive endpoint); if offline, transition the whole run to `paused(offline)` rather than burning per-agent retry budgets, then poll at ~30–60s with jittered per-agent resume on reconnect</INFERENCE>.

**UI state vocabularies (verbatim).** GitHub Actions conclusions: `success, failure, neutral, cancelled, skipped, timed_out, action_required, stale` — `neutral`/`skipped` don't fail the suite [docs.github.com](https://docs.github.com/en/rest/checks/runs?apiVersion=2022-11-28). CircleCI has a live degraded state `FAILING` distinct from terminal `FAILED`, plus `ON HOLD` for approval gates [circleci.com](https://circleci.com/docs/guides/orchestrate/workflows/). Buildkite: `soft_failed` is a boolean *field* on a failed job, not a state — the canonical "failed but don't fail the build" channel; job states include `blocked_failed`, `waiting_failed`, `timing_out` [buildkite.com](https://buildkite.com/docs/apis/rest-api/builds). Prefect separates `Failed` (code raised) from `Crashed` (infrastructure fault) and has `AwaitingRetry`/SCHEDULED, `Retrying`/RUNNING, `Paused` vs `Suspended` [docs.prefect.io](https://docs.prefect.io/v3/concepts/states). <INFERENCE from="these four vocabularies; the current bug where a run with dead agents reports 'completed'">the Workflow UI needs at minimum: per-agent `retrying (attempt k/30, next in Ns)`, `paused(offline|usage-limit|manual)`, `failed(terminal)`, and a run-level `completed_with_failures` distinct from `completed` — the current conflation of the last two is precisely what every surveyed system's `neutral`/`soft_failed`/`Crashed` vocabulary exists to prevent</INFERENCE>.

#### 1.3 Live queue mutation and message-passing

Temporal's three channels define the taxonomy: **Queries** (read-only, non-blocking), **Signals** (async fire-and-forget writes, no response), **Updates** (synchronous, validated — "you can validate the Update before accepting it into the Workflow and its history"; GA, with Update-with-Start GA in server v1.28.0) [docs.temporal.io](https://docs.temporal.io/encyclopedia/workflow-message-passing). The unbounded-queue pattern is signal-handler-appends + loop-drains + Continue-As-New before history limits (warn 10,240 events/10MB, terminate 51,200/50MB) [docs.temporal.io](https://docs.temporal.io/workflow-execution/continue-as-new) [docs.temporal.io](https://docs.temporal.io/self-hosted-guide/defaults). LangGraph computes fan-out width at runtime — `[Send("generate_joke", {"subject": s}) for s in state["subjects"]]` — and mutates thread state externally via `update_state(config, values, as_node=...)` [docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/graph-api). Airflow's `expand()` caps runtime fan-out at `max_map_length=1024` and marks zero-length input `SKIPPED` [airflow.apache.org](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/dynamic-task-mapping.html). All of these are durable actor mailboxes: serialized, journaled message delivery as the *only* mutation channel (Akka mailboxes / Orleans turn-based grains) [doc.akka.io](https://doc.akka.io/libraries/akka-core/current/typed/mailboxes.html).

<INFERENCE from="Temporal Signals-vs-Updates; the Workflow runtime's single-process JS script model; journal keyed by prompt-chain">for a single-process CLI runtime, the minimal mechanism is a watched command file or IPC socket polled between scheduler ticks — a mailbox the running script drains at safe points (before each agent dispatch). Mutations that fit the journal model cleanly: append work items (new prompts → new sha256 keys, no replay conflict), cancel pending items (mark-skipped before dispatch), reprioritize. Mutations that don't: removing an in-flight agent (requires abort semantics), and any mutation that would change an already-journaled prompt-chain (breaks the cache-prefix invariant — the Temporal analogue is that you can't rewrite history, only append). Message-passing *to* a running agent mid-LLM-call has no precedent in any surveyed system; all deliver at step boundaries.</INFERENCE>

#### 1.4 Workflow templating

The strongest extraction-target shape is **Prefect's**: parameter defaults (`parameters: dict`) plus a machine-readable `parameter_openapi_schema` auto-generated from function type hints via Pydantic, with `enforce_parameter_schema` rejecting nonconforming runs [docs.prefect.io](https://docs.prefect.io/v3/concepts/deployments). The reference/registry model is **Argo's**: named cluster-resident `WorkflowTemplate` objects invoked via `templateRef {name, template}` with per-call `arguments.parameters`, or whole-workflow instantiation via `workflowTemplateRef` where workflow-level arguments override template defaults [argo-workflows.readthedocs.io](https://argo-workflows.readthedocs.io/en/latest/workflow-templates/). GitHub Actions contributes the versioning discipline: pin by ref, "Using the commit SHA is the safest option" [docs.github.com](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows). Temporal contributes signature stability: "only take a single argument that is an object/dataclass of fields that can be added to as needed" [docs.temporal.io](https://docs.temporal.io/develop/python/workflows/basics).

On *automatic* extraction from ad-hoc definitions: `<MISSING_DATA>`No off-the-shelf tool performs the full loop "diff concrete instances → identify varying literals → promote to typed, defaulted, schema-validated parameters." Closest components: AWS HealthOmics auto-parses a parameter template from the workflow definition when the field is blank; Google Dataproc's manual field-path promotion; JSON-schema inference libraries (`@jsonhero/schema-infer`, `jtd-infer`) that cover the typing half from observed values.`</MISSING_DATA>` <INFERENCE from="Workflow scripts already carrying an `args` global and pure-literal `meta` blocks; Prefect/Argo models">templating for the Workflow tool reduces to: save script + a JSON-schema for `args` (inferred from the literal values in a concrete run via schema-infer-style tooling, defaults = the original literals), store under a name, instantiate as script+args — the runtime already separates the two.</INFERENCE>

#### 1.5 Maintaining a patch against the minified cli.js bundle

Ranked by durability across releases:

1. **Network-layer injection (no patch)** — Claude Code honors `ANTHROPIC_BASE_URL`; a local gateway adds retries transparently. LiteLLM proxy: `num_retries` (default 3), exponential backoff, per-error-class `retry_policy` (`RateLimitErrorRetries`, `TimeoutErrorRetries`, `InternalServerErrorRetries`), cooldowns and fallbacks [docs.litellm.ai](https://docs.litellm.ai/docs/proxy/reliability); claude-code-router is the same pattern purpose-built for Claude Code (routing, retries, key rotation — no cli.js modification) [github.com](https://github.com/musistudio/claude-code-router). Survives every release. **Limits:** reaches only HTTP behavior — cannot implement pause/resume UI, queue mutation, or workflow-run state. Sharp edges: a stray `ANTHROPIC_API_KEY` silently bypasses the gateway; LiteLLM releases 1.82.7/1.82.8 shipped credential-stealing malware — pin a known-clean version [github.com](https://github.com/BerriAI/litellm/issues/24518).
2. **Runtime source rewrite at load (the recommended code-layer mechanism)** — inject via `NODE_OPTIONS="--require ./shim.js"` (CJS) / `--import` (ESM); hook `Module.prototype._compile` (or ESM `load` hook via `module.register()`/`registerHooks()`, Node 22+) to rewrite the bundle's source string in memory before evaluation. This is the one loader hook that reaches bundle internals, because esbuild scope-hoisting erases internal `require()` boundaries — `require-in-the-middle`/`require.cache` interception only reaches genuine externals (`node:https`, `fs`) [esbuild.github.io](https://esbuild.github.io/content-types/). Gotcha: the V8 compile cache can serve bytecode compiled from unpatched source; mitigate with `NODE_DISABLE_COMPILE_CACHE=1`, and note core maintainers have signaled declining support for CJS-loader monkey-patching [nodejs.org](https://nodejs.org/api/module.html). The disk-patching alternative (tweakcc's model, including `node-lief` extract/repack for the native-binary install) is overwritten on every update and must be reapplied [github.com](https://github.com/Piebald-AI/tweakcc).
3. **Patch expression: Vencord's find/replace grammar** — `{find: <stable string literal>, replacement: {match: /regex with \i identifier wildcards and capture groups/, replace: "$1…$self.hook($2)"}}`. Anchors on content minifiers preserve (error messages, API field names, property names) rather than identifiers; the `\i` matcher survives per-release renames; the Companion tooling asserts each anchor matches exactly one site before shipping [deepwiki.com](https://deepwiki.com/Vendicated/Vencord/3.2.2-code-patching-mechanism). ast-grep/semgrep structural patterns (`$OBJ.foo = function() { return $F($X) }`) are the more robust alternative where the region is parseable in isolation [ast-grep.github.io](https://ast-grep.github.io/). Naive string/sed patching without this discipline degrades silently — tweakcc's failures against CC 2.1.76 were all regex-match misses, and the community shell patcher skips patches silently when strings vanish [github.com](https://github.com/Piebald-AI/tweakcc/issues/611).
4. **Fail-closed fingerprinting** — per patch, store `{anchor, matchRegex, sha256(matchedSlice)}`; at apply time require anchor uniqueness + hash match; on any mismatch, do not patch, surface "unsupported version X.Y.Z — running unpatched," never mis-apply. The production precedent is Atlas's `atlas.sum` checksum + `migrate validate` failing CI with non-zero exit on drift [entgo.io](https://entgo.io/blog/2022/05/09/versioned-migrations-sum-file/); ReVanced's method fingerprints (locate by opcode/string signature, not offset) are the same principle for binaries. Run a scheduled CI job installing each new `@anthropic-ai/claude-code` release and re-validating every anchor, so breakage is detected before users hit it.

Binary diff/fuzzy patching (bsdiff/Courgette/wiggle) is a poor fit: minifier renames change bytes everywhere, so a delta approaches a full-file replace with no semantic anchor `<CONFIDENCE:LOW>`— assessed by analogy; no CC-specific evidence`</CONFIDENCE:LOW>`.

<INFERENCE from="§1.5 items 1–4; the feature list (retry + pause/resume + UI + queue mutation + templating)">Build-vs-buy verdict for a solo maintainer: hybrid. Retry/backoff belongs at the network layer (gateway or an undici-dispatcher shim installed by the `--require` hook — interceptable because `fetch`/undici is a global/external surface) where it is release-proof; pause/resume, queue mutation, workflow UI, and templating require the in-memory source-rewrite path with Vencord-grammar patches, fingerprint-gated, with CI-per-release validation as the dominant ongoing cost. Expect the patch set, not the mechanism, to be the maintenance burden — tweakcc's history shows anchors decay within ~25 minor versions.</INFERENCE>

#### 1.6 Testing retry and recovery logic

- **Unit level (no real waits):** `@sinonjs/fake-timers` — `clock.tickAsync(ms)` (not sync `tick`, which skips interleaved promise resolutions) stepping past each expected delay, asserting attempt counts at each step [sinonjs.org](https://sinonjs.org/how-to/lolex-async-promises/). undici `MockAgent`: `setGlobalDispatcher(mockAgent)`, interceptors with `.reply(429)`/`.replyWithError()` and `.times(n)` — the canonical "fail twice then succeed" is two `.times(1)` error interceptors then a 200; `assertNoPendingInterceptors()` + per-interceptor `timesInvoked` verify the client actually made the expected retry sequence [github.com](https://github.com/nodejs/undici/blob/main/docs/docs/api/MockAgent.md). nock's documented gotcha doubles as an assertion primitive: interceptor consumption counts = retry counts [github.com](https://github.com/nock/nock).
- **Property-based:** fast-check's `fc.scheduler()` over async interleavings, generating (base, multiplier, cap, maxRetries, failure sequence of 429/500/ECONNRESET/timeout) and asserting invariants: delay monotone up to cap, attempts ≤ cap+1, Retry-After overrides computed backoff, jitter within bounds [fast-check.dev](https://fast-check.dev/docs/advanced/race-conditions/).
- **Integration:** llmock (OpenAI/Claude-compatible SSE mock; queues one-shot 429/503 errors that fire once then auto-remove — purpose-built for retry testing) [llmock.copilotkit.dev](https://llmock.copilotkit.dev/); MockServer for probabilistic 503s and 429-with-Retry-After quota simulation [mock-server.com](https://www.mock-server.com/mock_server/chaos_testing.html); Toxiproxy for transport pathology — L4 only (cannot synthesize a 429), but `limit_data` (close after N bytes) is exactly the mid-stream SSE-cut case, plus `latency`, `timeout`, `reset_peer` [github.com](https://github.com/Shopify/toxiproxy).
- **State of the art:** Temporal's time-skipping test environment fast-forwards through retry backoff intervals automatically [docs.temporal.io](https://docs.temporal.io/develop/typescript/testing-suite); Antithesis (FoundationDB lineage, public ~2024, $105M Series A) makes the *computer* deterministic via a hypervisor so unmodified stacks get replayable fault-injected timelines [antithesis.com](https://antithesis.com/blog/deterministic_hypervisor/).
- **The agent-specific gap:** 2025-era benchmarks inject tool/infrastructure faults to measure *agent behavior* (ReliabilityBench's λ-level infrastructure-fault tolerance [arxiv.org](https://arxiv.org/pdf/2601.06112); ToolMaze; AgentNoiseBench; the "Failing Tools" paper's argument that BFCL/τ-Bench/API-Bank are happy-path only [openreview.net](https://openreview.net/pdf/2be5795add6ec19f401efc71c99e69f5dea50e1c.pdf)), and agent-chaos injects LLM 500s/garbage tool output [github.com](https://github.com/deepankarm/agent-chaos) — but `<MISSING_DATA>`no established tool provides deterministic, seeded fault schedules across LLM calls + orchestrator retries, and no Toxiproxy-equivalent treats the semantic LLM failure taxonomy (429-with-Retry-After, truncated SSE, malformed tool-call JSON, content-filter refusal) as first-class toxics; llmock's one-shot error queue is the closest primitive`</MISSING_DATA>`.

### Q2. Current state and strongest supporting evidence

The field has converged (2024–2026) on a shared architecture: **durable journaled steps + server-side (out-of-process) retry state + typed terminal-error escape hatches + pause as a first-class state**. Strongest evidence: three independent systems shipped the same primitives on non-coordinated timelines — Temporal's Activity pause/reset-attempts (server v1.28.0, Public Preview) [docs.temporal.io](https://docs.temporal.io/activity-operations), native workflow-pause protos merged Oct 2025 [github.com](https://github.com/temporalio/api/pull/653), Restate's `on-max-attempts = "pause"` default [docs.restate.dev](https://docs.restate.dev/references/server_config), and Inngest's pause-with-skip-and-replay [inngest.com](https://www.inngest.com/docs/guides/pause-functions). In the agent-framework tier, the strongest-evidenced pattern is LangGraph's pending-writes mechanism — successful parallel siblings' outputs are persisted even when one branch fails, so resume doesn't re-run them [docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/persistence) — the exact fix for the Workflow tool's "one dead agent nulls out, siblings' work reported under 'completed'" failure.

### Q3. Contrasting viewpoints and competing evidence

- `<CONFLICTING_EVIDENCE>`**Should 429 be retried by default?** Yes: openai-python and anthropic-sdk-python both retry 429 with backoff by default (max_retries=2) [github.com](https://github.com/anthropics/anthropic-sdk-python). No: LangGraph's `default_retry_on` retries only 5xx and ConnectionError, deliberately excluding 429 [github.com](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py); the OpenAI Agents SDK ships retries *off* and makes 429 opt-in via `http_status([...])`. The disagreement is about layering: when the SDK below already retries 429, orchestrator-level 429 retries stack multiplicatively and can amplify overload (the Google SRE single-layer rule [sre.google](https://sre.google/sre-book/handling-overload/)). Resolution for the patch layer: own 429 at exactly one layer and neutralize the other.`</CONFLICTING_EVIDENCE>`
- `<CONFLICTING_EVIDENCE>`**Retry-forever vs bounded-then-park.** Temporal defaults to unlimited attempts bounded by timeouts; DBOS ships retries off (3 when on); Restate bounds at 70 then pauses. The SRE literature (3 attempts, 10% budget) sits far below all of them. The split reflects trust in error classification: unlimited retries are safe only when terminal errors are reliably classified out.`</CONFLICTING_EVIDENCE>`
- **Jitter:** the AWS canon says always-jitter [aws.amazon.com](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/), yet Temporal, Restate, and DBOS expose no user-facing jitter parameter (Temporal applies it only to internal infrastructure retries); Inngest and LangGraph jitter by default. For a single-user CLI the contention argument is weak per-user but real across the fleet (every client of api.anthropic.com backing off on the same overload event).
- **claude-flow:** marketing claims ("self-organizing agents with fault tolerance," "84.8% SWE-Bench") vs implementation evidence — issue #1397 documents agents as "database rows, not running processes" with no execution engine, and the current README has dropped the resilience claims [github.com](https://github.com/ruvnet/ruflo/issues/1397) `[SECONDARY: promotional]` applies to all claude-flow capability claims.

### Q4. What changed recently, and the trajectory

- **Pause became first-class (2025–2026):** Temporal activity pause (v1.28.0 Public Preview) and native workflow-pause API groundwork (Oct 2025) [github.com](https://github.com/temporalio/api/pull/653); previously pause was a Signal-handler pattern.
- **Error classification got richer:** Airflow 3.3's `ExceptionRetryPolicy` with per-exception `RetryRule`s, and the `common-ai` provider's `LLMRetryPolicy` — an LLM classifying errors into `rate_limit/auth/network/data/transient/permanent` [airflow.apache.org](https://airflow.apache.org/docs/apache-airflow-providers-common-ai/0.3.0/retry_policies.html) — signals a trajectory from status-code tables toward semantic classification.
- **Agent SDKs moved from implicit to explicit, composable retry:** OpenAI Agents SDK's 2025-era `ModelRetrySettings` with composable policies (`retry_after()`, `provider_suggested()`, `any()`/`all()`) and replay-safety guards (never retry a stream whose output already started) [openai.github.io](https://openai.github.io/openai-agents-python/models/) — the most modern config shape surveyed and a strong template for the patch layer's policy DSL.
- **Deterministic testing went mainstream:** Antithesis public launch and CockroachDB/WarpStream adoption (2024–2025) [warpstream.com](https://www.warpstream.com/blog/deterministic-simulation-testing-for-our-entire-saas); agent-robustness benchmarks emerged 2025 but tooling for agent-pipeline chaos remains a gap.
- **Claude Code patch ecosystem matured and demonstrated its failure modes:** tweakcc (extract/patch/repack incl. native binary via node-lief) and claude-code-router both active; tweakcc's cross-version regex decay (#611) is now documented prior art for why fingerprint-gated patching is mandatory [github.com](https://github.com/Piebald-AI/tweakcc/issues/611).
